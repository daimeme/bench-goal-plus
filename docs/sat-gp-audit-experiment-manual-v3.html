SAT → Goal-Plus · Audit–Repair Migration

从 SAT 团队协作到 Goal-Plus 候选审计：迁移方案与实验设计

SAT 的核心贡献不是固定角色本身，而是“主张—审计—修复”的结构化协作。Goal-Plus 候选彼此隔离、没有 peer 通道，因此本方案只迁移其中的审计回路：LLM Verifier 产出有界诊断，确定性 broker 合成 brief，候选按需拉取，N3 用候选回执和 hard evidence 完成闭环。N0–N3 实验只回答“审计生产、投递、闭环各带来多少增量”。

一页摘要

这份手册面向两类读者：第一次接触本方案的人，以及要复现 N0–N3 实验的人。它先解释为什么这样迁移，再给出可执行的实验设计；已有实现和待验证结果分开陈述，不把计划写成结论。

Migration

迁移什么

把 SAT 的“critic/repair”机制改造成 Goal-Plus 的 verifier audit → deterministic brief → candidate pull → response/credential。固定角色、peer messages 和团队阶段不迁移。

Attribution

怎么归因

N1−N0v 估计审计生产；N2−N1 估计投递；N3−N2 估计候选回执闭环；N2−N0v 给出审计总体效果。

Validation

一、问题：SAT 能提供什么，Goal-Plus 缺什么

SAT（Self-Organizing Agent Teams，arXiv:2609.22682）展示了固定团队、策略库和团队反思如何把“多个候选的探索”转化为可复用的协作计算。它同时暴露了一个更重要的问题：覆盖率不等于选择正确率，协作只有在审计和修复真正改变候选行为时才产生价值。

SAT

可迁移的机制

  • 一个候选提出主张，另一个角色用证据审计，提出有界修复。
  • 审计不是重新评分，而是把“缺什么证据、下一步查什么”变成可执行动作。
  • 协作策略需要被记录和复用，而不是只靠一次 prompt。
Goal-Plus

不能直接照搬的约束

  • 候选之间隔离，没有 peer message、共享草稿或固定 critic 可直接对话。
  • Verifier 是异步 FIFO；候选经常在审计产出前已经结束 turn。
  • FrozenSpec、hard verifier、Selection 和 Promotion 必须保持不可被审计改写。
  • 不能为审计新增队列、host wait loop 或候选轮询。
设计问题：在不引入 peer 通道、不改变 hard Evidence 的前提下，能否把 SAT 的“审计—修复”信号送达候选，并证明它改善答案，而不是只增加模型调用？

非目标

  • 不复制 SAT 的固定三角色、团队阶段或策略银行。
  • 不让审计改变 objective、acceptance、edit surface、预算、settlement 或 selection。
  • 不把“投递成功”当作“候选采纳”，也不把“候选采纳”当作“分数提升”。
  • 不在 hidden case 上训练或调参；hidden Judge 只做最终判定。

二、迁移方案：从 verifier/steering 分工到四个平面

先说设计起点，再说为什么改。迁移不是从“四个平面”开始的，而是从一个很自然的双角色映射开始，随后被 Goal-Plus 的异步 verifier、候选生命周期和 hard-evidence 边界逐步修正。

2.1 设计起点：把 SAT 的审计和修复接到已有平面

SAT 的协作可以拆成两个最小职责：audit（对主张提出反例、缺口和下一步检查）与 repair（按审计结果改变候选行为）。Goal-Plus 已经有两个看似对应的平面：

SAT 职责最初选择的 Goal-Plus owner预期承担的工作为什么先选它
critic / auditLLM Verifier提出 claim、定位 defect、给出下一步检查已经在 settlement 后独立评估，天然接近“critic”；不需要候选互相对话
explorer / repairSteering把修复动作送到候选，促使它改变下一次尝试已经有 candidate-visible 投递、attempt ledger 和 apply/shadow 概念

这个映射的价值是：不新增角色、不新增 peer 消息通道、不改变 hard Evidence，只用 Goal-Plus 已有的两个平面承接 SAT 的两个职责。它也是本方案最容易被理解的起点。

2.2 为什么原分工不能直接上线

把“verifier 审计、steering 修复”直接接起来后，四个约束同时暴露。它们不是实现细节，而是决定了最终架构：

原设想实际约束设计响应
verifier 产出诊断后，像 steering 一样 push 给候选verifier 是异步 FIFO；等它产出时源 settlement 往往已过期，候选也可能已 end_turn；steering 的发送窗口依赖 active call/source age改为持久化 + 拉取：候选在下一次 run_verifier/get_agent_context 取 brief
steering 的 repair 文案可以直接用于 VLIW旧 steering 主要消费 diagnostic text score 和 peer_reconciliation，既没有 VLIW 机器模型，也不是 hard fact重做审计内容：VerifierAudit + task reference + VLIW hard-fact producer
steering 发送成功就说明 repair 发生attempt ledger 证明“发过/返回过”，不证明候选改了 artifact，也不证明 hard score 改善增加候选回执 + credential：accepted/ignored/rebutted，后续 hard evidence 判 verified/rejected
只比较“有 audit / 无 audit”就能证明审计有效N0v 和 N1 的 verifier 调用次数不同，直接比较会把“多一次 LLM 调用”算进审计收益拆成 N0v/N1/N2/N3：compute-matched 后分别估计生产、投递、闭环

因此最终方案不是推翻“verifier 审计、候选修复”，而是保留职责分工，替换三件事：审计内容（从通用 steering 文案变成 verifier audit + VLIW facts）、投递方式（从 push 变成 pull）、闭环证据（从 attempt ledger 变成 candidate response + credential）。

2.3 收敛后的四个平面

最终系统分为 producer、composition、delivery、closure 四个平面。每个平面只拥有自己的事实和状态转换，这样 N0–N3 才能分别归因。

01 PRODUCERVerifier diagnosisLLM Verifier 输出 VerifierAudit；VLIW producer 叠加 hard facts
02 COMPOSITIONAuditBroker确定性合成 claim / ≤2 defects / repair，生成 AuditBrief
03 DELIVERYPull briefshadow 只持久化；apply 在候选下一次工具调用返回
04 CANDIDATERead / repair候选读取 claim、defect、repair 和 stop_condition
05 CLOSUREResponse + credentialN3 回执 accepted/ignored/rebutted；后续 hard evidence 判 verified/rejected

2.4 关键设计决策

下面这些选择看起来像实现偏好，实际上都是前面约束的直接结果。读这张表可以快速理解“为什么不是另一种更简单的做法”。

决策更简单的替代为什么不选代价 / 后果
用 verifier + steering 两个已有平面新增 SAT 固定角色或 peer 通道违反候选隔离；需要新的 host 通道和生命周期必须把 steering 的 transport 与 repair 职责拆开
确定性 broker 合成 brief让第二个模型写审计摘要增加成本与方差；同一 record 难幂等；容易引入 peer 推理brief 内容受 claim/defect 上限约束，解释力依赖 producer
拉取式投递沿用 steering pushverifier 异步、候选会 end_turn、source 会过期候选必须再次调用工具才会看到 brief
候选回执，而不是 verifier 自动修复让 verifier 直接改 candidate artifactverifier 不拥有 edit surface；会混淆评估与修复；hard Evidence 被污染N3 需要额外工具和 credential 状态机
N0v/N1/N2/N3 四组只跑 audit on/off无法区分生产、投递、闭环；也无法吸收 verifier 算力实验成本更高，但每个对比可解释
task reference 进入 verifier只看 diff 和 metrics无法判断 VLIW 语义、shape 泛化和评分合同freeze 时必须固定并 hash 任务文件

2.5 Producer：审计内容

Verifier 在评分之外返回一个有界 VerifierAudit：一个 falsifiable claim、最多 2 个 located defects、一个 repairable action。VLIW 额外叠加确定性事实：

事实来源defect含义
touched_denied_filesshortcut改动 evaluator、test 或 verifier 路径
changed_outside_allowedscope_driftdiff 超出允许 artifact/edit surface
controller_evidence.all_correct=falsesemanticspublic reference 对比在具体 case 失败
score_cycles > best_cyclesresource聚合 cycles 被慢 shape 主导，需 per-case 解释

隐藏 case 和 slot/register 上限尚未进入 verifier；它们属于 controller 侧后验判定，不在候选可见上下文中出现。

2.6 Composition：为什么 broker 不调用模型

Broker 只读终态 VerifierRecord，做确定性合成、identity、状态和过期。这样做的原因不是节省 token，而是保证“同一条 record 只产生一条 brief、重复投递幂等、审计不读取 peer 私有推理”。

2.7 Delivery：为什么是拉取

Verifier 是异步队列，等审计产出时源 settlement 往往已过期；候选也经常在结算后 end_turn。因此 brief 不在 verifier 消费时 push，而是持久化后由候选在下一次 run_verifier 或 get_agent_context 拉取。读取即标记 delivered，不重发。

2.8 Closure：N3 只增加“回执”，不增加新目标

N3 在 apply 之上增加 audit_closure=true。候选用 goal_plus_search_respond_audit_brief 回答 accepted / ignored / rebutted；accepted 创建一个 queued credential，下一次同一 candidate 的硬结算比较 before/after hard score 和 artifact hash，写入 verified 或 rejected。credential 是审计闭环证据，不是新的评分或 promotion 规则。

一句话：SAT 迁移到 Goal-Plus 的不是“团队”，而是“审计—修复”的可观测回路；不是“让候选互相对话”，而是“让 verifier 的诊断以有界、可回执、可验证的方式到达候选”。

三、四个平面的合同与不变量

实现边界比 prompt 更重要。下表是当前 runtime 的硬合同；任何实验臂只能切换模式，不能改写这些合同。

合同版本内容不变量
VerifierAuditvliw-audit/v1claim + ≤2 defects + repair引用只来自候选可见输入；零 defect 是合法 no-op
AuditBriefaudit-brief/v1claim + defects + repair + status + expiry同一 record 幂等；读取即 delivered；不改 hard Evidence
AuditRepairCredentialaudit-repair-credential/v1queued / verified / rejected + before/after artifact & hard score只由后续 hard settlement 关闭，不重跑 candidate
TaskReferencetask-reference/v1freeze 时读取的机器模型、约束、评分合同source 内、有界、带 hash；不包含 peer 或 hidden case

不变量清单

  • Advisory：brief 不改变 objective、acceptance、budget、edit surface、settlement、selection 或 promotion。
  • Isolation：候选只看到自己的 brief；broker 不读取 peer Record、排名或 Allocation。
  • Bounded：≤2 defects、≤1 repair、有界文本、有界 task reference、每 record 一条 brief。
  • Pull-only：不新增 verifier push、host wait loop 或候选轮询；shadow 永不投递。
  • Hard evidence 优先：审计失败只记录 warning，不阻塞 verifier 结算；credential 的 verified 只基于 hard score/artifact。
  • Frozen：N 组的 verifier、audit mode、task reference 和 closure 开关都由 controller overlay 在 freeze 时固定。

四、SAT 机制到 Goal-Plus 的映射

下面的映射回答“哪些 SAT 设计被保留、哪些被替换、哪些被明确舍弃”。它也是本方案与直接复刻 SAT 的边界。

六、假设与估计量

实验按“生产 → 投递 → 闭环”三段拆分。每段只有一个主终点，避免用总分掩盖机制。

假设对照主终点支持条件不能宣称
H1 审计生产N1 − N0vaudit precision / auditable rate / briefs per record审计能产出可定位缺陷，且不显著增加 harm不能宣称投递有效；N1 不投递
H2 投递N2 − N1official score（主）；delivery rate、uptake、repair lift投递可达、候选有行为变化、分数方向为正且 CI 支持不能宣称闭环有效；N2 无回执
H3 闭环N3 − N2verified rate、repair lift、harm、time-to-repair回执后 credential 可验证，且改善大于 harm不能宣称“协议更好”；只改变闭环
H0 算力N0v − N0official score / cost可选；用于解释 verifier 调用本身的成本不能替代 N1/N2 的审计归因

统计单位与分析原则

  • 以 task × seed/campaign 为配对单位；同一 T、K、C、R 下比较。
  • 主报告用 paired difference + bootstrap 95% CI；同时给出 MDE，避免把“不显著”解释为“无效”。
  • Pi 与 Codex 不合并成一个大样本；分别报告，必要时再做 harness 分层。
  • 先报告机制计数和 delivery/uptake，再报告 official score；机制不成立时不解释分数。
  • 缺失或失败的 campaign 不进入均值；单独列出 incomplete 原因。

测量有效性

  • VLIW score 是 max cycles 时，必须同时报告 best/slowest case，不能只报平均值。
  • hidden Judge 只在最终评测使用；public feedback 不能替代 hidden 结论。
  • 审计 precision 需要独立标签；未标注 brief 记为 unknown，不记为 correct。
  • credential 的 verified 只表示“后续 hard score/artifact 改善”，不表示“具体 defect 语义被证明修复”。

十、分析计划

分析顺序固定，避免“先看总分再找机制”。每一步都保留可复核的 artifact。

步骤问题产物
1. 接线审计N1 是否产出、N2 是否送达、N3 是否回执？delivery rate、response counts、missing reasons
2. 审计精度defect 是否可定位、是否被独立标签支持？precision by kind、abstention、false-positive cases
3. 行为变化候选是否真的采纳并改变 artifact？uptake、artifact change、repair lift、harm
4. 分数效应N1−N0v、N2−N1、N3−N2、N2−N0v 的方向和 CI？paired table、bootstrap CI、MDE
5. 成本与边界token/cost 增量是否值得？哪些任务/形状无效？cost table、failure taxonomy

主对照

对比解释主指标不能宣称
N1 − N0v审计生产本身audit precision、auditable rate、briefs/record投递有效
N2 − N1投递增量（主终点）official score、delivery、repair lift闭环有效
N3 − N2闭环增量verified/rejected、repair lift、harm协议更好
N2 − N0v审计+投递总体official score、cost生产/投递各自贡献
负结果也有信息：如果 N1 有产出但 N2−N1 无效应，优先检查 delivery/uptake；如果 delivery 高但 repair lift 低，检查 defect 是否可执行；如果 N3−N2 变差，检查回执是否诱导了过度修复。

附录

A. 旧 A1–A5 的处理

A1–A5 是 SAT-GP 旧阶梯：A1 是 Goal Plus 基线，A2 加共享，A3 是旧 diagnostic shadow，A4 是 push steering，A5 是固定协议 + push。它们混合了共享、识别、push 和协议四个因素，不能回答“新 audit 的生产/投递/闭环”问题。

因此 A1–A5 只保留为历史对照或迁移前证据，不进入 N0–N3 主矩阵；报告若引用旧数据，必须标注不同 T、不同合同、不同投递边，且不做配对检验。

B. 状态与文件位置 
.gp/runs/<run_id>/verifier/records/        # 终态 VerifierRecord
.gp/runs/<run_id>/audit/briefs/             # audit-brief/v1
.gp/runs/<run_id>/audit/credentials/        # audit-repair-credential/v1

brief 与 credential 都是 append-only 语义；credential 的 after 字段只在后续 hard settlement 关闭时写入。读取这些文件的脚本不应修改状态。

C. 术语
  • Producer：产生 claim/defect/repair 的 verifier 侧。
  • Broker：把 producer 结果合成 brief 的确定性组件。
  • Shadow：只生产、不投递。
  • Apply：持久化并在下一次工具调用投递。
  • Closure：候选回执 + credential 的 hard-evidence 关闭。
  • Compute-matched：N0v 与 N1/N2 近似相同 verifier 调用，只差 brief 通道。
D. 文档定位

本手册是设计 + 实验计划，不是运行日志或修订记录。实现状态以代码和测试为准；实验结果只在“结果”章节填入，并保留原始 campaign、brief、credential 和 summary 作为证据。
